# params.json に足すなら、という提案

`params.json` は書き換えていない。ここは「解析を回すのに必要だったが params.json に
無かった数値」と、その根拠を残す場所（`sensors/PARAMS_ADDED.md` と同じ役目）。

値の実体は `analysis/config.py` の `ANALYSIS` にあり、各項目に `_source` を付けてある。
params.json に取り込むなら `analysis` セクションを 1 つ足す形になる。

## 1. 足すことになる項目

| キー | 値 | なぜこの値か |
|---|---|---|
| `analysis.run.duration_s` | 480 | タクト 2.4 s × 8 ステーション = 1 回転 19.2 s。480 s はちょうど 25 回転。次数比の窓を回転で割り切るために整数回転に合わせた |
| `analysis.run.startup_revolutions` | 3 | ホルダが 1 本ずつ埋まるのに 8 サイクル（1 回転）。そのあと過渡が減衰するのにさらに 2 回転（水平合力が 1 サイクルあたり約 1/3 に落ちる）。合わせて 3 回転を捨てる |
| `analysis.segment.base_revolutions` | 1 | 1 回転ちょうどの窓にすると、次数 1 が DFT のビン中心に乗る。矩形窓のままで整数次どうしが漏れずに分離できる |
| `analysis.segment.envelope_revolutions` | 4 | 軸受の衝撃は 1 回転あたり 3.58 回しか出ない。4 回転 = 76.8 s で 14 発。`SENSORS.md` の「60 s 以上」も満たす |
| `analysis.spectrum.psd_resolution_hz` | 0.125 | 定常応答はタクト周波数 1/2.4 = 0.4167 Hz の高調波の線スペクトルになる。隣の線と混ざらないよう分解能をその 1/3 以下に取った |
| `analysis.spectrum.slosh_band_ratio` | [0.90, 1.10] | 減衰比 0.005 なので共振の半値幅は 0.04 Hz しかないが、液深が浅い側では f1 が下がる（120 mm で 3.751 Hz、20 mm で 3.381 Hz）。満量まわりの変動を拾える幅として ±10 % |
| `analysis.spectrum.defect_order_band_ratio` | [0.90, 1.10] | 欠陥次数 3.58 は非整数なのでビン中心に乗らない。窓の主ローブぶんの余裕 |
| `analysis.envelope.band_ratio` | [0.70, 1.40] | 帯域通過の幅。減衰 5 % の共振（半値幅 10 %）を十分に包む。広すぎれば雑音を、狭すぎれば衝撃の立ち上がりを落とす |
| `analysis.envelope.lowpass_ratio` | 0.20 | 包絡線の低域通過をリンギングの 20 %（3 kHz なら 600 Hz）に。見たい欠陥通過周波数 0.19 Hz よりはるかに高く、搬送波の 2 倍より十分低い |
| `analysis.envelope.filter_order` | 4 | 解析側の帯域通過。センサ層の 2 次と違い、ここは後処理なので零位相（filtfilt）で掛ける。実効 8 次相当 |
| `analysis.envelope.impact_threshold_sigma` | 5 | 衝撃のイベント検出。中央値 + 5 × 中央絶対偏差から出した σ。平均と標準偏差だと衝撃自身が基準を持ち上げる |
| `analysis.angle_resample.samples_per_rev` | 1024 | 角度の刻み 6.1e-3 rad。最大角速度 0.785 rad/s のとき 1 kHz サンプリングの角度前進は 7.9e-4 rad なので、いちばん速い瞬間でも 1 刻みに 7.8 点ある |
| `analysis.angle_resample.samples_per_rev_envelope` | 4096 | 包絡線は 1600 Hz まで間引いてあるので細かく取れる。次数 2048 まで見える |
| `analysis.detect.target_false_alarm_per_month` | 1 | 特徴量は 1 回転（19.2 s）に 1 個 = 1 日 4500 個。月 1 回未満に抑えるなら片側確率 7.4e-6 |

## 2. 「正常」を何にするか（数値ではなく取り決めの話）

`params.json` の `faults.fill_imbalance.volume_ratio` は 0.7（30 % 不足）で、これは
故障の値としては妥当。しかし正常側の値が無い。

排出ステーションが未実装なので、故障を一つも入れないと 8 本のホルダが完全に同じ状態になり、
水平合力がベクトル和でぴったり打ち消えて 0 になる（実測で 1e-10 N まで落ちる）。
これを「正常」にすると、基準がセンサの雑音そのものになってしまい、
どんな微小な異常でも巨大な検出余裕が出る。試験になっていない。

そこでこの解析では、正常側にも 1 % の充填ばらつき（`--fill-ratio 0.99`）を敷いた。
充填機で 400 mL に対し 4 mL のばらつきは、あって当たり前の水準。

params.json に足すなら、こうなる。

```
"tolerance": {
  "fill_volume_scatter_ratio": 0.01,
  "source": "正常運転でもホルダ間にこの程度の充填ばらつきはある。
             ばらつきゼロだと水平合力が完全に打ち消えて、監視の基準が作れない"
}
```

ただし、これは私が置いた仮定であって、外から決まる仕様ではない。
実機の充填精度が分かればそちらに差し替えるべき。

## 3. params.json の側で直したほうがよいと思ったもの（触っていない）

1. `faults.backlash` の既定値では、線形スロッシングの適用範囲を出る。
   `angle_deg = 0.3` / `impact_torque_Nm = 0.5` で回すと `dz/R` が 0.35 に達し、
   限界 0.20 を大きく超える。衝撃トルクを 0.02 Nm まで下げても、バックラッシュ角を
   0.02 deg まで下げても、`dz/R` は 0.2 を割らない（歯当たりそのものではなく、
   遊びを詰め終わった瞬間の負荷側の加速が効いている）。
   バックラッシュの検出は成立するが、そのときスロッシングの値は信用できない。

2. 正常運転でも `dz/R` の最大が 0.199 で、限界 0.20 の目前にいる。
   割出しを 1.5 s に延ばして dz/R を 0.1 以下に収めたつもりでも、
   480 s 回すと 0.199 まで上がる（ホルダが埋まるにつれ負荷慣性が変わり、
   固定ゲインの制御が過渡的に強く振るため）。24 s しか回さないと 0.187 で止まるので、
   短い試走では気づかない。基準点をもう少し内側に置くなら、割出しを 1.6〜1.7 s へ。
