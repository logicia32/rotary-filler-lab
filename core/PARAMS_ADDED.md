# params.json に足したい定数（core 側から）

`params.json` は読むだけで書き換えない、という決めごとに従って、こちらに書く。
rev.3（カム式インデックスユニット）へのコア書き直しで出てきたぶんに全部差し替えた。

## 無いと式が書けなかった / 仮置きで逃げたもの

どれも **`py/ref.py` も同じ所で止まっている**。値が入るときは両方に入れること。

| 要る値 | 何に使うか | いまどうしているか | 効き方 |
|---|---|---|---|
| ノズル出口から液面までの落差 | 噴流の着液速度 `sqrt(v^2 + 2gh)` | 既定 0（`filler --jet-fall` で入れられる） | 50 mm で力が +12 %。曲げモーメントに直に乗る |
| 受け渡し（星車）の衝撃の振幅・リンギング周波数・減衰比 | イベント種別 `infeed` / `discharge` | 時刻と質量だけ出し、振幅は 0 | センサ層が受け渡しの当たりを合成できない |
| 停留開始から受け渡しまでの遅れ | 受け渡しの時刻 | 停留開始と同時 | 段差の位置が動くだけ |
| 星車がボトルを押し出すのに掛かる時間 | 受け渡しの段差の鈍り | 1 ステップで飛ぶ理想化 | 下の「足さなかった理由」を参照 |
| 旋回軸受の摩擦トルク | `T_table` | 0 | **定速区間のトルクが厳密に `c_visc*om` になるのはこの欠落のため** |
| 減速機の効率 | モータ軸トルク | 1.0 | モータ軸の値を出していないので今は効かない |
| モータのトルク電流係数と無負荷電流 | インバータ出力電流 | **電流を出していない**。列にも無い | 電流を主張に使えない |
| テーブル板から支持部までの距離 | 曲げモーメントの腕 | 水平力による曲げを入れていない | 重量経路 2.2 N m に対し水平経路は 0.05 N m の桁 |
| ボトルの重心高さ | 転倒しきい値、水平力の腕 | センサ側の `arm_length_mm = 150` を流用する話になっているが、コアでは使っていない | 転倒余裕 12 倍という主張が追えない |
| `indexer.allowable_inertia_kg_m2` | 機構が成立するかの判定 | `null` のまま | **未確認。割付を 270 から 180 deg にすると許容値は 0.44 倍に落ちる** |

## 摩擦の 3 つは「足りない」ではなく「出所が無い」

`indexer.efficiency = 0.85` / `input_drag_torque_Nm = 0.30` / `table_viscous_Nms_rad = 0.05`。
`_friction_grade: "assumed"` のとおり仮置きで、**入力軸ピークトルクの 42 % は引きずりが占める**。
コアはこの 3 つをダンプのヘッダ（`FORMAT.md` 1 節）に書き出している。
あとからデータだけで「どの値でその結果になったか」を追えるようにするため。

## コードの中に持っている定数と、params に出さない理由

| 定数 | 値 | 場所 | なぜ params に出さないか |
|---|---|---|---|
| `TWIN_MAX_EVENTS` | 16 | `twin.h` | 1 積分ステップに同時に立ちうるイベント数の上限。実装の都合であって機械の性質ではない。溢れたら数えて報告する（既定では最大 3 件） |
| `TWIN_MAX_SCHED` | 512 | `twin.h` | 1 タクトぶんの予定イベント（軸受 268.5 件 + カムフォロワ 2 件）の置き場。超えると起動時にエラーで止める |
| `TWIN_EPS1` | 1.8412 | `twin.h` | `J1'(x)=0` の第 1 根。式そのものから出る定数で、諸元ではない。`params.json` の値ではなく解析式の値を使い、一致することを単体試験で見ている |
| `TWIN_RANGE_DZR` | 0.2 | `twin.h` | 線形スロッシングの適用範囲（`py/ref.py` の `TILT_INVALID_RATIO`）。文献から来る値で、この機械の諸元ではない |

## 足さなかった理由（星車の押し出し時間）

いまの実装は、停留に入った瞬間にボトルが消えて空瓶が現れる、という理想化になっている。
そのため `V` / `h` / `phi` / `J_load` / `M_bend` / `f_tab_*` が 1 ステップで飛ぶ
（`FORMAT.md` 2.8 節に飛ぶ量を書いた）。読む側から見ると、タクトに同期した段差が
必ず信号に入ることになる。

実機の星車は有限の時間を掛けて押し出すので、本当はその時間で力が抜けていく。
入れるなら `stations.transfer_time_s` を置いて、その間に液の質量を線形に抜くのが素直。

**足さなかった理由**: この機械の実物を見ていないので、その時間を決める外からの情報が無い。
停留 1.5 s の中に収まるはず、までしか言えず、そこで適当な数を置くと
「外から決まる仕様だけを置く」という `params.json` の建て付けを壊す。
段差が入ることを `FORMAT.md` に明記して、読む側が承知した上で扱えるようにするほうを選んだ。

検出層で段差が邪魔になり、かつ「押し出しに掛かる時間」の根拠が立つなら、
そのときに `params.json` へ足すのが順序として正しい。
