# core — C99 物理コア（params.json rev.3）

ロータリー充填機の仮想モデルのうち、物理を計算する部分。外部依存は libm だけ。
`malloc` は使わない。数値は `params.json` から読む（コードに直書きしない）。

機械は**カム式インデックスユニット＋誘導ギヤモータ**。位置ループも速度ループも
電流ループも無く、テーブル角はカム入力軸角 `psi` の関数で一意に決まる。

- **仕様書は `py/ref.py`。** 式・符号・積分の順序はすべてそちらに合わせてある
- 出力の取り決め: `core/FORMAT.md`。**バイナリの並びはこの文書が唯一の正**
- 式の背景: `MODEL.md`（機械の物理）と `SENSORS.md`（センサ）。
  `py/ref.py` と食い違うところは下の「既知の食い違い」に名指しで挙げた

## ファイル

| ファイル | 中身 |
|---|---|
| `twin.h` / `twin.c` | 物理コア本体。JSON パーサも中に持っている |
| `main.c` | 単体実行の CLI。`filler` になる |
| `test_twin.c` | 単体試験。諸元から出る量を期待値と突き合わせる（95 件） |
| `dumpio.py` | `RFILL004` / `RFEVT002` の読み込み。**外（sensors / analysis / viz）からも使える** |
| `compare_ref.py` | C と `py/ref.py` の突き合わせ。しきい値の根拠は先頭に書いてある |
| `check_events.py` | イベント列が取り決めどおりかの確認 |
| `check_steady.py` | 供給と排出を入れて定常状態になるかの確認 |
| `FORMAT.md` | 出力バイナリ（連続ログ・イベント列）の全オフセット |

## ビルド

```
make            # filler と libtwin.so
```

`-O2`。**`-ffast-math` は付けない**（演算順序が変わると `py/ref.py` との突き合わせが
成立しなくなる）。警告は `-Wall -Wextra -Wshadow -Wconversion` で 0 件。

## 走らせる

```
./filler --cycles 10 --out out.bin      # 10 タクト（30 s）
./filler --help                         # 全オプション
make run                                # 1 タクトだけ
make dataset DUR=30                     # 正常 + 故障 4 種
```

1 回走らせると **ファイルが 2 つ** 出る。`out.bin`（連続量のログ、`RFILL004`）と
`out.bin.events`（イベント列、`RFEVT002`）。分けてある理由は SENSORS.md 5.5 節
（軸受のリンギング 3 kHz は 4 kHz のログでは折り返す）。
rev.3 では**連続ログに衝撃系の列を一切置いていない**。イベント列が唯一の出どころ。

読むのは `core/dumpio.py`。numpy 以外に依存しないので、`sensors/` `analysis/` `viz/` から
そのまま import できる。旧版の列名からの移行表は

```
../.venv/bin/python dumpio.py --migration
```

で出る。`sensors/read_dump.py` は 001 / 002 専用で 004 は読めない
（下の「センサ層への移行」）。

計算の速さの目安: 既定パラメータ（`dt = 2.5e-5 s`、8 ステーション）で
**実時間 30 s ぶんが CPU 2.0 s**。ログは 4 kHz で 912 kB/s。

## 試験

```
make test       # 下の 4 つを全部（1 分ほど）
make unit       # C 単体（1 秒）
make compare    # py/ref.py との突き合わせ（40 秒。参照側が純 Python で遅い）
make events     # イベント列の確認（5 秒）
make steady     # 定常状態の確認（5 秒）
```

`PY` で Python を差し替えられる（既定は `../.venv/bin/python`）。numpy が要る。

### 1. `make unit` — C 単体（95 件）

期待値は `py/ref.py` の実測値。カム曲線（`Ca`/`Cv`・継ぎ目の連続性・`S(1)=1`）、
運動学、慣性、トルクと出力の走査、スロッシング、割出し 1 回の応答、
充填と噴流、垂直荷重、ホルダ番号と工程、1 タクト回した結果、軸受イベントの数。

**期待値を書き換えて合わせにいかないこと。** ずれたら `params.json` か実装のどちらかが
動いている。

### 2. `make compare` — `py/ref.py` との突き合わせ（**これが本丸**）

前版は「割出し軸が作った加速度だけを共通入力にして、液まわりだけ比べる」形だった。
軸に制御ループがあり、その構成が C と `py/ref.py` で違ったためで、軸そのものは
比べられなかった。**rev.3 では制御ループが存在しない**ので、軸・慣性・トルク・曲げ・
スロッシング・充填・受け渡しまで丸ごと同じ土俵に乗る。

`filler --f64` が吐いた 24000 レコード（2 タクト）を、同じ `params.json` で回した
`py/ref.py` の `simulate()` と 1 レコードずつ比べる。正常時と、故障 4 種を全部
有効にした場合の 2 通り。

#### 通ったときの数字（2026-07-23 版 004、既定パラメータ、2 タクト = 24000 レコード）

| 量 | C と参照実装の差（最大値で正規化） | しきい値 |
|---|---|---|
| `t` / `psi` / `th_t` / `omega` / `alpha` / `th_m` | **0.000e+00**（完全一致） | 1e-13 |
| `torque_table` / `torque_input` / `torque_slosh` | **0.000e+00** | 1e-11 |
| `m_bend_y` / `f_tab_x` / `f_tab_y` | **0.000e+00** | 1e-11 |
| `m_bend_x` | 0 〜 3.6e-17 | 1e-11 |
| `m_bend`（`hypot` を通る） | 1.9e-16 | 1e-11 |
| `j_load` | 1.6e-16 | 1e-11 |
| ステーション `V` / `phi_t` / `phi_r` / `spill` | **0.000e+00** | 1e-12 |
| ステーション `h`（`V/A` を作り直す） | 2.6e-16 | 1e-12 |
| ステーション `present`（在荷） | **0**（完全一致） | 0.5 |
| イベント（軸受 537 件・カムフォロワ 4 件・受け渡し・液垂れ）の時刻 | **0.000e+00 s** | 1e-12 |
| イベントの振幅・モータ軸角 | 8e-9 〜 4e-8 | 1e-6 |

トルクの符号と項（`- T_slosh`、`dJ/dt*omega`、効率の場合分け）を入れ替えたあとも
**ビット一致が保てている**。

**倍精度の量はほぼ全部ビット一致した。** 残る 1〜2 ulp は `hypot` と `V/A` の
再計算だけで、そこも 1e-16 台。イベントの 1e-8 台は、イベント列を f32 で書いている
ぶん（f32 の丸めは相対 6e-8）で、それ以上ではない。

しきい値を実測より 5 桁以上高く置いてあるのは、丸め以外の違い（式が違う、順番が違う）が
入ったらすぐ分かるようにするため。根拠は `compare_ref.py` の先頭に書いた。

`py/` は読むだけで直さない。合わない箇所が出たら、差の出どころを特定して報告する。
参照実装を答えに合わせて動かしたら検証にならない。

### 3. `make events` — イベント列

- ヘッダの実効値が、その回に実際に使った値になっているか
- 軸受が**時間軸で等間隔**か（ずれ 0.00 ps）、**停留中も打っている**か
  （1 タクト 268.5 件のうち 536/1074 が停留中。前版はテーブル軸に置いていて
  1 サイクル 0.44 回だった）
- 軸受のモータ軸角が `motor_speed * t` と合うか（相対差 7.6e-8 = f32 の丸め）
- カムフォロワが割出しの入口と出口だけか（1 サイクル 2 件）
- 受け渡しのホルダ番号が `holder_at()` と合うか
- **衝撃が連続量に漏れていないこと**。カムフォロワ＋軸受を有効にしたダンプが、
  正常時と **1 ビットも違わない**（連続量の 10 列を `array_equal` で比較）

### 4. `make steady` — 定常状態（26 タクト）

- 満量のホルダ数が「滞留 - 1」本で一定（既定の工程角なら 5 本）
- ホルダごとの液量が 8 サイクル周期で繰り返す（差 8.2e-3 mL = 充填の量子化 `flow*dt` 1 回ぶん）
- `J_load` / `T_table` が 1 サイクル周期で戻る（差 8e-7 / 1.7e-6）
- 供給から排出まで 6 割出し = 18.0 s（イベント列から数える）
- 入る量と出る量が 400 mL / サイクルで釣り合う

`M_bend` だけ 600 点中 1 点が外れる。**弁が開く時刻（停留開始 + 0.08 s）が積分刻みの
格子とちょうど重なる**ので、サイクルによって開弁が 1 ステップ前後し、そこにログ点が
乗るとその 1 点だけ噴流（0.159 N m）の有無が入れ替わる。物理ではなく境目の丸め。
MODEL.md 7.1 節の PLC 5 ms 格子を入れれば消えるが、`py/ref.py` が実装していない。

## 2026-07-23 に直った食い違い（版 003 -> 004）

こちらから挙げた指摘のうち、`py/ref.py` 側が直り、C も追随したもの。
**版 003 のデータは捨てること。** 符号と並びが変わっている。

| 直したもの | 効き方 |
|---|---|
| `T_slosh` を引く向きに（MODEL.md 4.5 が正） | テーブル軸ピークトルク 1.3428 -> **1.4201 N m**（+5.8 %）。剛体換算 1.38748 の 1.0235 倍 |
| `F_react` を反作用側に統一（液も空瓶も `-m*a`） | 水平合力の**符号が反転**。大きさは変わらない |
| `f_tab_t`/`f_tab_r` -> `f_tab_x`/`f_tab_y`（世界 x, y の順） | 列の**中身が入れ替わる**。読む側は必ず直すこと |
| 在荷フラグ `present` を追加 | `V = 0` の空瓶と欠品が区別できるようになった |
| `steady_holders()` が工程配置から作るように | `--prime-ref` は不要になったので撤去 |
| 効率の場合分け（`T_table*om` の符号で `/eta` と `*eta`） | 減速側の過大 1.38 倍が消えた。`torque_input` が**符号付き**に |
| `dJ_load/dt*omega` の項 | 公称条件では厳密に 0。タクトを詰めると効く |
| 弁の閉じ遅れ故障が過充填に | 400.0 -> **449.5 mL**（+49.5 mL） |

## まだ残っている食い違い（直していない。報告だけ）

**`py/ref.py` が仕様なので、食い違ったときは ref.py に合わせてある。**

1. **`sensors/read_dump.py` は `RFILL004` を読めない。** 001 / 002 専用。
   下の「センサ層への移行」を参照。
2. **カムフォロワ摩耗のテーブル角オフセットが無い。** MODEL.md 8.4 節は
   `±clearance/2` を与えろと書いているが、接触剛性が `params.json` に無いので
   当たりはイベントだけにする、という判断（発注側の回答）。
   したがって連続量はカムフォロワ摩耗の有無で変わらない
   （それを `check_events.py` の 7 節が逆に不変量として使っている）。
3. **PLC の 5 ms 格子が無い。** 公称の開指令 1.550 s はもともと 5 ms 格子に乗るので
   入れても下の `make steady` の 1 点は消えない、という判断（発注側の回答）。
4. **こぼれは楔ではなく柱。** `py/NOTES.md` 6 節が 1〜2 桁の過大と指摘している。
   既定条件では液面が縁に届かないので効いていない。
5. **液が入っていないホルダは、空瓶の慣性反力も数えていない。**
   `py/ref.py` が `volume <= 0` のホルダを丸ごと飛ばしているのに合わせた。
   空瓶 1 本ぶん（0.011 N）が抜ける。
6. **旋回軸受の摩擦トルクが無い**（`params.json` に無い）。
   そのぶん定速区間が厳密に `c_visc*omega` になるのはモデルの都合であって物理ではない。

## センサ層への移行（`sensors/` は触っていない）

`core/dumpio.py` は numpy 以外に依存しないので、`sensors/` `analysis/` `viz/` から
そのまま import できる。移行に要るのは次の 4 つ。

1. **magic で振り分ける。** `dumpio.peek_magic(path)` が先頭 8 バイトを返す。
   `RFILL004` なら `core/dumpio.read_dump`、`RFILL001` / `002` なら
   従来の `sensors/read_dump.py`。
2. **列名を差し替える。** `dumpio.describe_migration()`（`python dumpio.py --migration`）に
   旧版からの対応表がある。**`T_slosh` と `F_tab_*` は符号も逆**なので、
   名前を替えるだけでは合わない。
3. **消えた列を作り直す。** `motor_torque` は `torque_input / gear_ratio`、
   `dz_over_R` は `tan(hypot(phi_t, phi_r))`、`range_flag` はヘッダの
   `range_exceeded` / `max_dz_over_R`。`motor_current` は**出せない**
   （トルク電流係数が `params.json` に無い）。
4. **衝撃はイベント列から合成する。** `a_bear` / `T_bl` の列は無い。
   `dumpio.read_events()` で読んで、各センサの刻みで減衰振動を作って足す
   （`FORMAT.md` 5.4 節に式）。**ここがいちばん作業量が大きい。**

`sensors/` の `structure_model`（grounded / free）や取り付け位置は前版の持ち越しのままで、
機械側が rev.3 に変わったことは反映されていない。そちらは別の判断が要る。

## `params.json` に足りないと感じた値

コアを書いていて、無いと式が書けなかった／仮置きで逃げたもの。

| 要る値 | 何に使うか | いまどうしているか |
|---|---|---|
| ノズル出口から液面までの落差 | 噴流の着液速度 | 既定 0（`--jet-fall` で入れられる）。50 mm 入れると力が 12 % 増える |
| 受け渡し（星車）の衝撃の振幅・リンギング周波数・減衰比 | イベント種別 2・4 | 時刻と質量だけ出し、振幅は入れていない |
| 停留開始から受け渡しまでの遅れ | 受け渡しの時刻 | 停留開始と同時 |
| 旋回軸受の摩擦トルク | `T_table` | 0。**モデルの定速区間が厳密に `c_visc*om` になるのはこの欠落のため** |
| 減速機の効率 | モータ軸トルク | 1.0 |
| モータのトルク電流係数と無負荷電流 | インバータ出力電流 | **電流を出していない**。列にも無い |
| テーブル板から支持部までの距離、ボトルの重心高さ | 曲げモーメントの腕 | 水平力による曲げを入れていない（重量経路だけ） |
| `indexer.allowable_inertia_kg_m2` | 機構が成立するかの判定 | `null` のまま。**未確認** |

## 主張の範囲

**実機の実測ではない。合わせ込みもしていない。** 言えるのは
「この物理とこの諸元の下ではこうなる」までで、それ以上は書かない。

摩擦の 3 つ（効率 0.85 / 引きずり 0.30 N m / テーブル粘性 0.05 N m s/rad）は
**出所の無い仮置き**で、入力軸ピークトルク 0.7155 N m の 42 % は引きずりが占める。
**入力軸トルクとモータ電流を主張の根拠にしないこと。**

支持部の曲げについて言えるのは「重量経路が水平反力経路より 1 桁半大きい」までで、
その比（既定条件で 31.8 倍）は**腕の長さ 0.150 m という仮置きの上に乗っている**。
`m_bend` と `torque_slosh` を比べた 51.6 倍は別の量どうしの比で、この主張には使えない。
